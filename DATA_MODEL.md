# ProtocolPulse — Relational Data Model and Synthetic Fixture Contract

**Freeze:** `PP-S2-CF-20261114-01`, schema design `1.0.0-rc1` (pending approval). **Engine:** SQLite via SQLAlchemy 2.0 ORM/Alembic, Python 3.12. All tables use snake_case physical names, API exposes the canonical snake_case DTOs in API_CONTRACTS. `ID` = nonempty stable `VARCHAR(64)` unless noted. `source_id` is a logical identifier with explicit `source_version`; database FK targets a source-row surrogate where necessary. `*_at` always UTC in DB; protocol/site calendar windows use IANA timezone and local `DATE` fields.

## 1. Core relational invariants

- Only **synthetic** fixtures: exactly **15** patients, no real names, contact details, MRNs, addresses or live EHR links. `patient.synthetic_only=1` CHECK; trial.synthetic_only likewise. The older specification's 250-record scenario is overridden by the newer user data instruction, but fixture IDs `P-042`, `P-175` etc. remain.
- Structured clinical facts are authoritative input to deterministic evaluation; narrative is independently sourced. Conflicting note assertion creates `OpenItem`/`UNKNOWN` until documented reconciliation. A narrative never mutates a structured fact and can be displayed as a **claim** with evidence and review state.
- Every clinical fact/observation has clinical timestamp or onset/local date/uncertain interval, recorded timestamp, ingestion timestamp, logical `source_id`/`source_version`, evidence quality and evidence state. Facts with no measured value use `NULL` plus `NOT_RECORDED|NOT_ASSESSED|UNCERTAIN|NOT_APPLICABLE` as appropriate, not a fabricated negative. `EXPLICITLY_NEGATIVE` requires affirmative source/reconciliation coverage, not `NULL` by itself.
- All `CriterionResult` and `PatientTrialAssessment` rows are immutable and reference frozen criterion set hash, `EvidenceSnapshot`, engine version, evaluation instant and triggering event if monitoring. `EVALUATION_ERROR` returns **null** candidate status. Old data does not get updated during late-event processing.
- Medication type `ORDER|DISPENSE|ADMINISTRATION|REPORTED_USE|DISCONTINUATION|CANCELLATION` remains separate, including orders after an administration; no auto-conversion to proof of ingestion. Study-product exposure is **separate** from concomitant medications and does not expose blind-breaking assignment.
- Soft deletion only for nonclinical UI drafts before approval (`deleted_at`, revised state); approved criteria, source evidence, events, assessments, clinical decisions, finding history, approvals, audit and protocol bytes **cannot hard-delete** in an operating demo. Only explicit `seed --reset-demo` removes a fully synthetic local DB and resets fixtures after confirmation.

## 2. Essential SQLAlchemy tables, keys, columns, constraints and indexes

Conventions: `PK` primary key, `FK` foreign key, `UQ` unique, `CK` check. All row mutable status changes increment `revision INTEGER NOT NULL DEFAULT 1`; every update uses optimistic guard. Immutable tables still have `revision` or `source_version` for replay. `created_at`/`updated_at` UTC recorded by server; SQLite stores fixed-width UTC ISO text via a SQLAlchemy `UTCDateTime` TypeDecorator (parse to aware datetime, fail on naive dates), not inconsistent local timestamps. `json` columns stored as validated JSON strings with SQLAlchemy JSON type and application schema checks; indexed clinical fields use concrete typed columns.

## 3. Precise six-state evidence and contradiction semantics

| Evidence state | Stored meaning | Can independently prove no contraindication? |
|---|---|---|
| `NOT_RECORDED` | No chart assertion found or a gap registry indicates absence of documentation | **No** |
| `EXPLICITLY_NEGATIVE` | A sourced negative finding/statement, qualified by temporal and reviewer-approved completeness | **Potentially**, only if adequate for that specific rule/window |
| `NOT_ASSESSED` | Clinician/study has not assessed the topic | **No** |
| `NOT_APPLICABLE` | Field does not apply under a documented rule/scope | Not evidence of absence; should usually skip only when approved rule allows |
| `UNCERTAIN` | Conflicting, vague, insufficient-quality, imprecisely dated statement | **No** |
| `POSITIVE` | A sourced positive assertion/observation with provenance and evidence quality | May establish `FAIL` where applicable; does not imply drug harm |

Use separate `evidence_quality` (`HIGH|MODERATE|LOW|UNVERIFIED`), `verification_status` (`VERIFIED|UNVERIFIED|CONFLICTED`) and **clinical state** (`ACTIVE|RESOLVED|SUSPECTED`) so an explicitly negative note is not confused with a resolved condition. A complete no-use reconciliation is an individual `PatientFact` under `domain_section='medication_reconciliation'`, with `coverage_start_at`, `coverage_end_exclusive_at`, `reviewer_actor_id`, `reviewed_at` in its validated `value_json`, source refs, and explicit negative state. Its coverage window must fully cover `[2026-10-01,2026-10-31)` to support `PX-EXC-02=PASS`; a medication list without such assertion cannot.

**Narrative conflict sequence:** `clinical_note` source span says drug continues; structured med statement says stopped → persist both as distinct facts → create `open_item(reason_code=CONFLICTING_SOURCES,blocking=1)` → deterministic relevant rule returns `UNKNOWN` unless verified source reconciles; agent may find corroborating evidence but never changes the medical state by assertion alone.

## 4. Effective time, overlap, replay and corrections

- `recorded_at` = source signed/entered data, `ingested_at` = local system arrival; `effective_at` = clinically relevant occurrence, independent of those clocks. `observed_at` and specimen date used for observations, `decided_at` for reviewer. All UTC instants offset-aware. Human-facing `2026-10-31` comparison uses `Europe/Athens` calendar.
- Dose administration with exact timestamp is a **point** tested as `start <= t < end`. Medication interval `[a,b)` overlaps rule window `[c,d)` iff `a < d AND c < b`; unknown end is **not** automatically infinity. Store possible intervals for partial dates; evaluate `UNKNOWN` if any valid interpretation changes the result.
- Prescription and dispensation timestamps remain evidence-of-order/supply. Last dispensation date does not prove use. A `DISCONTINUATION` event stops a prior order/report only when explicit source/version link supports that interpretation, not every historical administration.
- A correction is an immutable new `PatientEvent` or fact version referencing `supersedes_*`; do not edit/deletes original, mark superseded at query resolution, retain old `EvidenceSnapshot` membership for original assessment replay. Late entry 2026-11-21 effective 2026-11-19 must recompute relevant monitoring rule under event time and show ingestion delay.
- Snapshot hash is deterministic sorted concatenation of `evidence_kind:evidence_id:source_version` plus clinical watermark; canonical JSON used in hashed data. Replay needs original engine, criterion-set hash, terminology-map hash, evidence set and evaluation local-date policy. If engine version unavailable, return `REPLAY_UNAVAILABLE`, not guessed equality.

## 5. Database transaction recipes and uniqueness

**Approval transaction**: lock logical protocol version via revision check → validate 8 rules and all coverage items → check qualified investigator synthetic actor → append eight `CriterionApproval` rows and signed coverage hash → update `Criterion` statuses and version state/active pointer → append audit → commit. If any step fails, rollback all. Partial UQ active version ensures at most one `ACTIVE` version.

**Event T1**: compute canonical body hash; check existing `(patient_id,source_event_id,source_version)` and idempotency record. If same payload, return original `EventReceipt` and job (even when job already SUCCEEDED); if mismatch return `409`. Else insert event, reference source, idem row, `Job(INGEST_EVENT)`, audit; commit. `recorded_at` retained as user-supplied source time. Do not use a message queue with at-most-once semantics.

**Event T2**: atomically claim job once; construct new snapshot including event and relevant fact versions; evaluate only rule dependencies; create immutable monitoring assessment/results; insert `MonitoringFinding` on unique fingerprint; upsert `ReviewCase` by `issue_key`; append audit; job `SUCCEEDED`; commit as one transaction. On violation rollback and retry boundedly; do **not** roll back accepted event from T1. Optional AI job queued separately afterward; LLM call outside transaction.

**Case review transaction**: optimistic revision and valid state transition + actor check; append `ReviewDecision`, update `ReviewCase.status/revision`, append audit; commit. Reopen after new material evidence via documented system case reopen action and audit, preserving old decisions. A database error is operational `FAILED`, not clinical `UNKNOWN`.

## 6. Exact 15-patient fixture / source sections

Fixture registry ID list: `P-042,P-175,P-124,P-161,P-117,P-118,P-083,P-140,P-151,P-201,P-202,P-203,P-204,P-205,P-206`. First nine are verbatim acceptance archetype IDs. Each narrative is concise (e.g. 80–160 words) and references its own note/source; no patient is a real person.

Production would split and qualify additional coded domains and source-text provenance. Every generated 15-patient record must be checked against a JSON schema fixture and a per-patient completeness audit—this is a **planned seed obligation**, not a claim that 15 full records are already generated.

## 7. Schema evolution, migration/seed order and FHIR R4 boundary
